# DIROMA Business OS — Usanidi / Setup

## Kwa Mmiliki (lugha rahisi)

Huhitaji kuandika code. Hatua zinazokuhitaji wewe binafsi ni hizi tu, na hakuna inayohitaji kulipa kwa sasa:

1. **Fungua akaunti ya Supabase (bure kwa majaribio).** Nenda supabase.com, jisajili kwa email yako ya biashara, na washa MFA kwenye akaunti hiyo. Hii ni akaunti ya *mtoa huduma*. Wafanyakazi hawatahitaji email.
2. **Unda "project" mpya** iitwe `diroma-staging`. Hii ni ya majaribio tu: hakuna takwimu halisi za biashara.
3. **Mpe anayesimika mfumo ruhusa** kupitia mwaliko wa Supabase ("Invite member"). **Usitume** nenosiri wala "secret key" kwenye WhatsApp au chat.
4. Anayesimika mfumo atakupa **code ya usanidi ya mara moja**. Fungua `<anwani-ya-app>/setup`, weka code, jina lako, namba yako ya simu, na nenosiri lako (angalau herufi 12).
5. **Washa MFA:** pakua app ya *Google Authenticator* au *Microsoft Authenticator*, scan QR code inayoonekana, kisha weka tarakimu 6.
6. **Ongeza wafanyakazi:** nenda **Timu → Alika mfanyakazi**. Mfumo utakuonyesha code ya kuwezesha **mara moja tu**.
   - Mpigie mfanyakazi kwenye namba hiyo kuthibitisha ni yake.
   - Mpe code ana kwa ana.
   - Yeye atafungua **Wezesha akaunti** na kuchagua nenosiri lake mwenyewe. Wewe hulijui nenosiri lake.
7. **Mfanyakazi akisahau nenosiri:** Timu → ⋯ → andika sababu → **Toa code mpya**. Akaunti yake inafungwa papo hapo hadi atakapoweka nenosiri jipya.
8. **Mfanyakazi akiondoka:** Timu → ⋯ → andika sababu → **Ondoa**. Hapo hapo hapati tena data yoyote.

## For the implementer (technical)

### Requirements
- Node 22+, a Supabase project (Free tier is fine for staging).
- Auth settings in Supabase dashboard:
  - **Phone provider enabled** (Authentication → Sign In / Providers → Phone). Phone + password sign-in uses
    `signInWithPassword({ phone, password })`. Routine login sends **no SMS**.
  - **MFA → TOTP enabled** (Owner and Manager are forced to `aal2` by the database).
  - **Disable public sign-ups** (Authentication → Settings → "Allow new users to sign up" off). Staff accounts are
    created only by the server after an Owner invitation.
  - Minimum password length 12.
  - SMS provider: **not needed** for Milestone A. Activation/recovery is Owner-supervised in person (see below).
    Configure an SMS provider only after the Owner approves its cost.

### Tests
```bash
npm test          # unit tests (phone normalization, password policy, role routing)
```
```bash
npm run test:db   # real PostgreSQL 16: migrations + RLS/permission/activation/audit tests
```
`test:db` runs on a throwaway local PostgreSQL cluster with a small emulation of Supabase's `auth` schema
(`tests/db/00_supabase_stub.sql`). That stub also reproduces Supabase's default broad grants to `anon`/`authenticated`,
so the tests prove that the migration's revokes actually work. It does **not** test Supabase Auth itself (sign-in, MFA, admin API).
Those must be verified against a real Supabase project (see `docs/PROGRESS.md`, "Pending verification").

### Enrollment and recovery model (Milestone A)
- **Owner:** one-time setup code (bcrypt-hashed, 24h, 5 attempts, single use), generated by the installer. The installer verifies the
  Owner's identity and phone in person before handing over the code. The auth user is created with `phone_confirm: true`
  and `app_metadata.enrolled_via = "owner_setup_code"`. This is **not** SMS proof of possession.
- **Staff:** the Owner (MFA-verified) invites → the server creates the auth identity with a random, never-displayed password →
  issues a one-time activation code (hashed, 24h, 5 attempts). The Owner verifies the phone by calling it and hands over the code
  in person. The worker sets their own password on `/activate`. The membership has no data access until activation completes.
  Every step is written to the audit log.
- **Recovery:** the Owner resets access, which immediately moves the account to `pending_activation` (all data access cut), and a new code is
  issued. Owner-account recovery is a separate procedure and is not yet implemented (see PROGRESS).

### Security invariants enforced in the database
- Business authority comes only from `memberships` (status `active`). It is re-checked on every query and RPC, so suspension takes effect
  even while a JWT is still valid.
- Owner and Manager privileges require `aal2` (MFA) at the database level, not just in the UI.
- Clients cannot write any table directly. All writes go through `SECURITY DEFINER` functions with an empty `search_path`
  and explicit permission checks.
- `audit_log` is append-only (update/delete/truncate blocked by trigger, even for the table owner).
- Exactly one Owner. Nobody can grant the Owner role or change their own role or status.

### Scheduled daily reports
- Set `CRON_SECRET` (`openssl rand -hex 32`) in the hosting environment. `vercel.json` schedules `/api/jobs/daily` at 20:30 UTC
  (23:30 Dar, "interim") and 21:15 UTC (00:15 Dar, "final" for the previous day). Vercel Cron sends `Authorization: Bearer <CRON_SECRET>`.
- Manual run (e.g. to test): `curl -H "Authorization: Bearer $CRON_SECRET" "https://<app>/api/jobs/daily?kind=interim&trigger=manual"`.
- Results, failures and PDF downloads (60-second signed links) appear in **Control Center**. See `docs/RECOVERY.md` for backups.
